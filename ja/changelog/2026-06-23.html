資産インスペクタ + 停止を伴わないスイッチ + Windows サポート

オープンソースのリリース後、この日は徹底的な磨きと強化の作業でした。編集者はあらゆる種類のアセットをカバーするインスペクターを獲得しました。シーン間、および編集と再生間の切り替え時に、レンダラーがコールド リブートされたり、黒い画面でフリーズしたりすることがなくなりました。 Windows の互換性の問題のバッチが解決されました。エンジンはデバイスの損失から自己修復することを学習し、制約された環境では正常に機能を低下させます。ロード時の契約チェックが追加されました。そしてターミナルバージョンはチェックポイントの巻き戻しを獲得しました。

リリース後、研磨に転じる

オープンソース化によりプロジェクトは一般に公開され、引き渡された瞬間から本当のテストが始まります。より多くの人々、より多様なコンピューター、より多くの批判的な目が、滑らかさや安定性が十分でない箇所をすべて明らかにすることになります。この日はリリース後の順番でした。目もくらむような新機能を追うのではなく、既存のエクスペリエンスをよりスムーズに磨き上げ、基礎をよりしっかりと固めることに落ち着きました。アセット インスペクターを使用すると、クリエイターは手元にあるすべての素材を明確に確認できます。ストールフリーのスイッチングにより、日常使用で最も頻繁に発生する問題が解消されます。 Windows との互換性により、より多くの人が参加できるようになります。エンジンの自己修復機能により、事故による人員の中断が容易に防止されます。また、読み込み時のコントラクト チェックにより、AI のコード編集でエラーが発生するのを防ぎます。個々に小さなものではありますが、これらはすべて「実際にスムーズに使用でき、安定して使用できるかどうか」を目標としています。これはまさに、一般公開されたばかりのプロジェクトが即座に強化する必要があることです。第一印象は一度だけであり、リリース後のあらゆる磨きがそれを守ります。

アセットインスペクター: すべてのアセットを明確に表示

この日、編集者はプロジェクト内のあらゆる種類のアセットをカバーするアセット インスペクター パネルを獲得しました。これは、基本的でありながら長い間欠落していたニーズに対応します。つまり、プロジェクトにメッシュ、マテリアル、テクスチャ、アニメーション、シーンなどのマテリアルが大量に蓄積されている場合、どのようにしてそれらが実際に何であるかをすぐに確認できるでしょうか?以前は、名前だけが表示されることが多く、その外観やプロパティを知るには、実際にシーンに配置する必要がありました。ここで任意のアセットを選択すると、右側のインスペクターに適切なプレビューと詳細が表示されます。メッシュを選択するとその形状が表示され、マテリアルを選択するとそのテクスチャの品質が表示され、テクスチャを選択すると画像が表示され、アニメーションとその情報が表示されます。素材パネルには「コンテンツブラウザ」も連携し、閲覧から閲覧、編集まで一貫した流れを形成しました。クリエイターにとって重要なのは、「自分が何を持っているかを把握する」ことです。少し大きなプロジェクトには簡単に数十、数百のアセットが含まれており、それぞれを開いて明確に確認できるため、曖昧な名前の山の中を手探りする必要がなくなり、素材の管理と再利用の効率が向上します。

停止せずに切り替える: レンダー コンテキストを維持する

この日は、長い間悩まされ、日常使用において非常に頻繁に発生していた古い問題、つまりスイッチング時のストールが修正されました。以前は、異なるシーン間を切り替える場合でも、「編集」モードと「再生」モードを切り替える場合でも、システムは基礎となるグラフィックス レンダリング全体を破壊して再構築しました。つまり、黒いフラッシュ、再初期化、そして最も遅い場合は完全なフリーズが発生しました。根本原因: スイッチごとにレンダー コンテキストが再構築され、グラフィックス コンテキストの再構築は、特定のブラウザ環境ではエラーが発生しやすいかなり高価な操作です。切り替えの頻度が高くなるほど、中断される可能性が高くなります。この日のソリューションは「キープアライブ」です。切り替えによって破棄して再構築することはなくなり、レンダー コンテキストをバックグラウンドで生きたままにし(破棄するのではなく画面外に移動し)、必要に応じて直接再利用します。インプレイスに切り替えると、シーン間や編集と再生間の切り替えがスムーズかつ瞬時になり、黒い画面や停止が発生しません。 「微調整、一瞥、再度微調整」を繰り返すことを促す作成ツールにとって、切り替えは最も頻繁にトリガーされるアクションの 1 つです。このパスを「毎回再構築」から「いつでも即時切り替え」に変えることで、クリエイティブ フローの最も障害となる滞りが直接取り除かれます。

クロスプラットフォーム: Windows 修正のバッチ

Windows がオープンソースになり、できるだけ多くの人に使ってもらいたいと考えた今、Windows は取り組む必要がありました。この日、一連の Windows 互換性問題が一斉に発生しました。これはすべて、「別のシステムでは問題ないが、Windows では不可解に壊れる」という典型的な種類の落とし穴です。プロセスがまだ生きているかどうかを判断する方法を Windows ターミナルで正しくするには、別のアプローチが必要です。新しいプロジェクトを作成するときに作成されるシンボリックリンクは、Windows の権限制限に達し、ネイティブの Windows 同等のリンクで回避されます。また、環境マップ (HDR 形式) のデコードも Windows で修正されました。起動スクリプトは、クロスプラットフォームで使用できるように強化されました。それぞれの問題は目立たないものですが、未解決の問題が 1 つあると、Windows ユーザーのインストール時、プロジェクト作成時、または最初の実行時にブロックされ、完全にバウンスされる可能性があります。インストールから実行、Windows 上での作業に至るまでのこのプロセス全体を取得することは、デスクトップ市場の大半を握る Windows ユーザーに扉を開くことになります。そして、より多くの人に試してもらいたいオープンソース化されたばかりのプロジェクトにとって、このステップの実用的な重要性は特に大きいのです。

エンジンの自己修復: デバイスの損失から回復し、制限内で正常に機能を低下させます。

この日、エンジンは「事故への耐性」において大きな一歩を踏み出した。 1 つはデバイス/表面の自己修復です。グラフィックス デバイスは、さまざまな理由 (システム リソースの圧迫、ドライバーのリセット) で動作中に突然低下することがあります。以前は、回復せずに画面が真っ暗になることがよくありました。現在、エンジンはそのような低下を検出し、レンダリングを自動的に再確立しようとするため、画像が停止するのではなく元に戻ります。 2 つ目は制限下でのグレースフル デグラデーションです。一部の弱いブラウザ環境では、エンジンのビデオ メモリ容量のプローブが正確な値を取得できない可能性があり、今日では取得できない場合は安全なデフォルトの上限に戻ります。また、レンダリングするコンテンツが容量を超えると、フレーム全体をスキップするのではなく、「切り詰められたサブセットをレンダリング」し、画像全体をクラッシュさせるよりも少し描画を少なくすることを優先します。低レベルのクラッシュも回復可能なエラーとして分離されました。共通のテーマは「回復力」です。あらゆる種類の実際のデバイスに直面し、一般の人が長期間使用することを目的としたエンジンは、すべてが完璧であると想定することはできません。真の成熟の証しは、不完全性が生じても、最初の事故でストライキを起こすのではなく、耐え、回復し、低いレベルで働き続けることです。

ロード時の契約チェック + シーンのライトバック

この日、「AI がコードを書き込む」ラインに、読み込み時の契約チェックという別の安全策が追加されました。ゲームをロードすると、システムはゲーム コードがエンジンのインターフェイスと一致していることを自動的に検証します。「コントラクト」とは、エンジンが規定する呼び出し規約です。 AI がコードを編集した後、インターフェイスの一部の誤用やファイル間のインターフェイスが一致しない場合、システムは途中で不可解にクラッシュするのではなく、画面上のエラー オーバーレイでこの「ドリフト」を直接かつ目立つように指摘します。これにより、「書き込み完了」と「実行中」の間に別の自動チェックポイントが効果的に設定され、インターフェースレベルのエラーがその場で捕捉されます。一方、エンジンはシーンの「ライトバック」を完了しました。エンジンは、現在のシーンのコンテンツを構造化アセット パックにシリアル化し、コンテンツから識別子を逆に検索できます。これにより、「エディターで編集してすぐに保存する」というループの基礎が築かれます。編集とは、単に表示して調整することではありません。変更は確実に持続する必要もあります。これら 2 つを順番に行うことで、「作成された製品」の信頼性が高まり、コードが整列し、編集結果が確実に保存されます。

ターミナルチェックポイントの巻き戻し + マルチエージェントのコラボレーションタッチ

この日、コマンドライン/ターミナル バージョンには、グラフィカル インターフェイスに一致する機能 (チェックポイントと巻き戻し) が追加されました。会話を以前のチェックポイントにロールバックして再試行し、満足できない場合はバックアウトできます。セッションリカバリが追加されました - 中断後、1つのコマンドが中断したところから再開され、最初からやり直す必要はありません。さらに、質問用のオーバーレイも表示されます。チャット インターフェイスは、マルチエージェント コラボレーションのライブ詳細を磨き続けました。サブエージェントがタスクを別のエージェントに渡すと、明確なリレー ヘッダーによってハンドオフ関係が示されます。関連エージェントは「プロデューサー ファミリ」ごとにグループ化され、それぞれが独自のカテゴリに分類されます。電話が必要な機密性の高い操作には、専用の許可確認カードが用意されています。また、エージェントのアバターはわずかに持ち上げられて拡大され、「誰がアクティブで、誰があなたを待っているか」が一目で明確になりました。これらは一緒になって 1 つの役割を果たします。異なるタスクを負った AI のチームに協力を指示する場合、プロセス全体が明確で、制御可能で、常にロールバック可能でなければなりません。つまり、停止と巻き戻しの主導権を維持しながら、AI が何をしているのかを理解できるのです。

この日が意味するもの

前日のオープンソースリリースが「ドアを開けて人々を招き入れる」日だったとすれば、この日は「人々が快適に暮らせるように家を整える」日だった。画期的な新機能はなく、全体的に洗練され、強化されていました。すべての資産を明確に確認できるようにし、切り替えが滞らないようにし、Windows ユーザーをドアの中に入れ、エンジンが事故に耐えられるようにし、AI のコードがエラーで逃げるのを防ぎ、マルチエージェントのコラボレーションを明確かつ制御可能にしました。これらすべてが示しているのは、「使いやすさ」と「信頼性」です。まさに、大量の新規ユーザーを迎え入れたばかりのプロジェクトが一度に最も強化する必要がある 2 つのことです。新しいユーザーは、目もくらむような機能を求めて留まるのではなく、Windows での動作が 1 回停止したり、クラッシュしたり、失敗したりするだけで離れてしまう可能性があります。これらの目立たないエクスペリエンスと安定性の問題を 1 つずつ解決することは地味に見えますが、オープンソース化に続く実際の使用に向けて基盤をより強固にすることになります。リリースは出発点であり、終わりではありません。この日が「実際に人に使われる」ということを真剣に考え始めた日でした。
