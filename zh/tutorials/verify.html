构建、检查并验证真正运行的游戏

一份代码 diff 不是可玩结果。天工引擎为 AI 客户端提供多层独立证据，让它分清“代码编译了”和“游戏真的能玩”。

优先使用能覆盖真实玩家路径的最窄证据。截图、结构化状态检查与真实 GPU 执行回答的是不同问题，任何一种都不能替代全部。

四层证据

  1. 项目身份 — 修改前确认项目根目录、活动游戏、Runtime 版本与 Engine SDK commit。 forgeax://status
  2. 构建与启动 — 构建或复用选定 Runtime，拿到准确预览地址与日志路径。 forgeax_run_current_game
  3. 玩家行为 — 打开真实浏览器构建，操作移动、交互、状态转换与响应式 UI。 Play URL
  4. 引擎证据 — 行为异常时检查运行状态、渲染事实、结构化错误、性能记录或帧捕获。 Remote · Profiler · RHI debug

天工引擎怎样帮助定位问题

天工引擎会暴露通常被黑屏或模糊 bug 报告遮住的状态：

现象应该检查的证据它能区分什么
页面空白或物体消失renderer.frustumStats、相机状态与 pass 名称相机 / 裁剪错误，还是网格 / 材质确实缺失。
输入或玩法状态像是“死了”ECS World、查询、调度与 Remote 状态实体 / 组件缺失，还是系统没有运行。
插件或配置更新失败Cordis Entry / Fiber 状态与结构化错误码配置无效，还是生命周期 / 清理问题；失败更新可以保留上一份可用 Fiber。
游戏卡顿或性能回退有边界的 CPU Profiler 捕获与真实 GPU 测量CPU 调度成本，还是 GPU / 渲染成本。
渲染输入看似正确，但像素结果错误RHI-debug 帧记录 / 回放：draw、binding、资源与像素渲染输入错误，还是 shader / 后端行为异常。

要求诊断，不要要求盲改

告诉智能体必须观察什么，并要求在报告中给出证据：

黑屏 / 空场景

Play 页面能打开，但场景看起来是空的。先诊断，不要直接改代码。
检查活动游戏与 Engine / Runtime 身份、浏览器和运行时错误、
renderer.frustumStats、相机朝向与渲染 pass。
只做最小修复，重新运行，并说明哪一项证据发生了变化。

输入与玩法

在真实 Play 构建里验证 WASD 与跳跃路径。
检查焦点 / 输入状态和消费输入的 ECS 系统。
不要只凭 TypeScript 报告完成；实际操作移动并解释观察结果。

性能

定位帧时间回退的原因。
使用有边界的 CPU profile 与可用 GPU / 渲染证据，对比修改前后，
同时保持视觉结果不变。分别报告测量结果与任何未验证层。

可信的完成报告应该包含什么

工作完成时，要求智能体把每一层证据分开报告：

  • 修改的游戏与文件——现在由哪些源码与资产路径负责这项行为。
  • 运行身份——成功启动时使用的 Engine SDK 与托管 Runtime。
  • 构建结果——当前游戏是否构建成功，以及实际操作了哪个 Play 地址。
  • 观察到的行为——真正测试了哪些操作、交互、状态与视觉。
  • 剩余不确定性——没有执行的验证层必须明确标成“未验证”，而不是暗示全部通过。
天工引擎把验证视为创作的一部分：检查真实状态，做聚焦修改，用准确 Runtime 运行，再用可观察证据闭合循环。
