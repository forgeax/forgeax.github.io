핵심 편집기 패널 도착 + Windows 지원

이날 편집기는 게임 편집에서 가장 중요하고 일상적인 세 가지 패널(계층 구조, 검사기, 자산)로 채워져 처음으로 완전한 편집 흐름을 형성했습니다. 그 사이에 엔진은 2D 타일 맵 렌더링을 추가하고, 일련의 Windows 호환성 문제를 수정하고, 가져온 모델 전체 장면을 샘플 게임에 연결했으며, 하위 서비스가 다운될 때 완전히 오류가 발생하는 대신 백엔드가 정상적으로 저하되도록 만들었습니다.

"skeleton"에서 "flesh"까지: 편집자가 채우기를 시작합니다.

지난 이틀 동안 편집자의 "골격"(도킹 가능한 패널 시스템, 변형 도구, 실행 취소/다시 실행)을 세웠습니다. 그러나 뼈대만으로는 일을 할 수 없습니다. 실제로 누군가가 앉아서 게임을 만들 수 있게 해주는 것은 그 뼈대에 걸려 있는 기능 패널입니다. 오늘의 작업은 정확히 그 뼈대에 살을 붙이는 것입니다. 모든 게임 편집기에 없어서는 안 될 세 가지 핵심 패널을 동시에 채워서 가장 기본적인 편집 흐름("객체 보기, 선택, 속성 변경, 자산 가져오기")이 처음으로 처음으로 엔드투엔드에서 실행됩니다. 동시에 엔진은 두 가지 방향으로 확장되었습니다. 즉, 2D 게임플레이의 전체 타일 맵 범주에 대한 렌더링 기반을 추가하고, 더 많은 사람들이 실행할 수 있도록 일련의 Windows 호환성 문제를 수정하는 것입니다. 가져온 모델이 실제로 샘플 게임에 연결되고 백엔드가 실패할 경우 우아하게 성능이 저하되므로 오늘의 주제는 분명합니다. 이전에 구축한 프레임워크를 한 지점씩 실제로 사용할 수 있는 것으로 채우는 것입니다.

핵심 편집기 트리오: Hierarchy / Inspector / Assets

이날 편집자는 게임 편집에서 가장 필수적인 세 가지 패널을 작성했습니다. 각 패널은 고유한 도메인을 염두에 두고 없어서는 안 될 요소는 없습니다. 계층 패널: 부모-자식 관계에 따라 장면의 모든 개체를 트리로 배열하여 누가 누구의 자식인지 한눈에 확인하고 클릭하여 선택합니다. 여기에서 장면의 "사물을 찾고 구조를 파악"할 수 있습니다. 검사기 패널: 개체를 선택하면 해당 개체의 모든 속성(위치, 회전, 재질, 직접 편집할 수 있는 모든 종류의 매개 변수)이 오른쪽에 펼쳐집니다. 여기에서 "한 가지를 조정"할 수 있습니다. 자산 패널: 모델, 텍스처, 장면 팩 등 프로젝트의 모든 자료를 찾아서 끌어오고, 필요한 것은 무엇이든 끌어서 "자료를 가져오는" 곳입니다. 세 가지가 함께 모든 게임 개발자가 하루에 수백 또는 수천 번 반복하는 핵심 흐름("모든 개체 보기 → 하나 선택 → 매개 변수 변경 → 자산에서 항목 드래그")을 형성하여 마침내 Studio에서 완성됩니다. 편집의 본질은 "전체 보기, 단일 개체 세부 사항 및 자료 소스" 사이를 끝없이 오가는 것이기 때문에 정확하게 "트리오"입니다. 이 세 가지가 모두 있어야만 편집자가 진정으로 작업을 수행할 수 있습니다.

엔진은 2D 타일 맵 렌더링을 얻습니다.

엔진은 오늘날 게임플레이의 전체 범주인 2D 타일 맵 렌더링의 토대를 마련했습니다. 타일 ​​맵은 고전적인 2D 게임 접근 방식입니다. 세계를 정사각형 셀의 격자로 자르고 각 셀에 작은 그림("타일")을 넣은 다음 이를 모아 전체 맵을 만듭니다. 잔디, 벽, 강 및 도로는 모두 이 작은 사각형으로 포장됩니다. 고전적인 횡스크롤, 하향식 및 픽셀 아트 게임이 거의 모두 이를 기반으로 구축되었습니다. 오늘 엔진은 타일 맵과 타일 레이어에 대한 기본 구성 요소를 탑재했으며 일반적인 타일 맵 파일 형식을 읽을 수 있습니다. 즉, 모든 셀을 손으로 교체하지 않고도 전용 맵 도구에서 그린 레벨을 엔진으로 직접 읽어서 렌더링할 수 있습니다. 의미: 이는 플랫폼의 범위를 이전의 3D 기반 장면에서 2D의 광대한 영역으로 공식적으로 확장합니다. 많은 제작자가 만들고 싶어하는 첫 번째 게임은 바로 2D 게임이며, 이 길을 열면 수많은 2D 제작자에게 문이 열리게 됩니다.

Windows 호환성: 더 많은 컴퓨터에서 제대로 실행됩니다.

오늘은 일련의 Windows 호환성 문제에 중점을 두었습니다. 크로스 플랫폼 소프트웨어의 가장 일반적이고 가장 교활한 함정은 종종 기능 자체에 있는 것이 아니라 시스템 간의 미묘한 규칙 차이에 있습니다. 운영 체제마다 서로 다른 텍스트 줄 끝, 서로 다른 파일 경로 구분 기호, 와일드카드 파일 일치에 대한 서로 다른 동작을 사용합니다. 그리고 어느 하나라도 정렬되지 않으면 한 시스템에서 제대로 실행되었던 코드가 다른 시스템에서는 이유 없이 실패합니다. 오늘은 이러한 차이점으로 인해 발생한 일련의 오류를 하나씩 수정하고 텍스트 줄 끝 규칙을 통합하여 모든 파일이 플랫폼 전반에서 일관되게 작동하도록 했습니다. Windows 사용자의 경우 이는 개발 환경과 테스트가 OS 차이로 인해 모든 곳에서 문제가 되는 대신 자체 컴퓨터에서 올바르게 실행된다는 것을 의미합니다. 가능한 한 많은 사람들이 사용할 수 있는 도구를 위해서는 크로스 플랫폼 지원이 불가피합니다. 새로운 기능을 추가하지는 않지만 얼마나 많은 사람들이 "접근할 수 없는"지 직접적으로 결정합니다. 이 호환성을 강화하면 더 넓은 사용자 기반을 위한 첫 번째 장애물이 제거됩니다.

"가져온 모델"을 실제 게임에 연결 + 더 견고한 백엔드

전날에는 "모델을 드래그하면 장면이 됩니다" 기능이 열렸습니다. 오늘은 실제 예를 통해 살펴보았습니다. "모델 가져오기 → 플레이 가능한 장면 조립" 경로의 실제 예로서 전체 장면 모델이 슈팅 샘플에 연결되었습니다. 새로운 기능을 단순히 실행하는 것만으로는 충분하지 않습니다. 실제 엔드투엔드 흐름에서 유지되는지 확인하려면 실제 사용 사례가 필요하며 이 샘플이 바로 그 기능을 수행합니다. 백엔드는 예상치 못한 일에도 더 잘 대처합니다. 종속된 하위 서비스가 아직 작동하지 않은 경우 관련 요청은 이제 전체 인터페이스를 끌어내리는 일반 서버 오류 더미를 발생시키는 대신 명확한 "일시적으로 사용할 수 없음" 상태로 우아하게 저하됩니다. 이 "우아한 성능 저하"는 강력한 시스템의 특징입니다. 하나의 구성 요소가 다운되어도 전체 시스템이 마비되어서는 안 됩니다. "이 부분은 지금은 사용할 수 없습니다"라고 명확하게 말하고 나머지는 계속 실행되도록 해야 합니다. 이전 바이너리 자산 업로드 채널과 결합하여 외부 자료를 가져와 실제 게임에서 사용하는 전체 체인이 오늘날 더욱 완벽해졌습니다.

오늘의 의미

이날은 획기적인 단 하나의 돌파구도 없었지만 제품이 "프레임워크에서 실용성으로 이동"하는 과정을 잘 보여줍니다. 편집자 트리오의 등장은 Studio의 시각적 편집이 처음으로 "시연 가능"에서 "실제로 앉아서 작업할 수 있음"으로 넘어갔다는 것을 의미합니다. 2D 타일 맵의 추가로 플랫폼의 영역이 3D에서 2D로 확장되어 클래식 2D 게임을 만들고 싶어하는 수많은 제작자를 사로잡았습니다. Windows 호환성 수정은 더 많은 잠재 사용자를 위해 미리 진입 장벽을 제거합니다. 종합적으로 볼 때, 이 세 가지는 같은 방향을 가리킵니다. 즉, 더 많은 사람이 더 많은 방법으로 더 많은 장치에서 이 플랫폼을 실제로 사용할 수 있도록 한다는 것입니다. 도구의 성숙은 결코 눈부신 기능의 탄생이 아니라, 이런 종류의 "적용 범위"와 "사용성"이 날로 확고히 확대되는 것입니다.
