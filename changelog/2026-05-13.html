前两天证明了"对话能做出能跑的东西",也立起了渲染、资产、安全这些地基。这天的主题,是把这条闭环从"能跑通一次"打磨成"用起来顺手"——让改动即时可见、让历史不会丢、让 agent 不会搞错对象。这些听起来都是"理所应当"的体验,但每一项背后都是一处真实的工程缺口被补上。当这些缺口都补齐,平台才从"能演示"变成"能长时间坐下来用"。The previous days proved "conversation can build something runnable" and raised the foundations of rendering, assets and safety. This day's theme is polishing that loop from "runs once" into "comfortable to use" — changes visible instantly, history never lost, the agent never confused about which target it's acting on. These all sound like experiences that "should just work," but behind each is a real engineering gap being filled. Only once they're all filled does the platform go from "can demo" to "can sit down and use for hours."

实时热重载预览:改文件,画面自己变Live hot-reload preview: edit a file, the picture changes itself

这天给中间的预览接上了一座"热重载桥":当某个游戏的文件发生变化,预览会自动刷新,把最新的样子呈现出来,而不需要你手动点重载。它的工作方式是后端持续盯着该游戏目录里的文件改动,一有变化就通过实时通道通知前端,前端随即让预览重新加载。这一步看似只是"省了一次点击",实则是"边说边看"闭环里至关重要的一环:agent 一改完代码,你几乎立刻就能在画面上看到结果,对话与画面之间的延迟被压到最低。对长时间坐着做游戏的人来说,这种"所改即所见"的即时反馈,是把灵感和实现连起来的关键。This day connected the center preview to a "hot-reload bridge": when a game's files change, the preview refreshes itself to show the latest, with no manual reload click. It works by the backend continuously watching for file changes in that game's directory and, the moment something changes, notifying the front end over a real-time channel, which reloads the preview. This may look like "saving a click," but it's a vital link in the "say it, see it" loop: the instant the agent finishes editing, you see the result on screen almost immediately, squeezing the latency between conversation and picture to a minimum. For someone sitting down to make a game for hours, this "what you change is what you see" instant feedback is what connects inspiration to implementation.

会话回放:重开一个会话,来回原样还原Session replay: reopen a session and the back-and-forth comes back

和 AI 协作久了,会话历史就是你的宝贵资产——里面有你提过的需求、它做过的决定、走过的弯路。这天把会话历史落到一份持久的"账本"里,并让重新打开一个会话时能从账本完整回放此前的来回。技术上特别处理了一点:实时事件流里只带"发生了什么"的轻量记录、并不含完整文本,所以回放要从账本里把真正的内容重新组织出来,而不是简单重播事件。意义在于:你关掉再回来,上下文不会丢;一段历史可以随时翻回去看,就像它当时发生的样子。这让"长期、多轮地做一个项目"成为可能,而不是每次都从一张白纸开始。Collaborate with AI long enough and the session history becomes a precious asset — the requirements you raised, the decisions it made, the detours taken. This day persisted session history into a durable "ledger" and made reopening a session replay the prior back-and-forth from it. One technical subtlety was handled: the real-time event stream carries only lightweight records of "what happened," not the full text, so replay must reconstruct the real content from the ledger rather than naively replaying events. The significance: close it and come back, and context isn't lost; a stretch of history can be revisited anytime, just as it happened. This makes "working on a project long-term, over many rounds" possible, instead of starting from a blank page each time.

着色器可组合 + 跨文件热更新Composable shaders + cross-file hot-reload

引擎这天给着色器加上了"可组合"的能力:着色器之间可以互相引入、共享片段、用宏定义参数化,而不必把所有代码都堆在一个文件里。更妙的是它支持跨文件的热更新——你改了被引用的那个公共片段,所有用到它的着色器都会跟着即时刷新。对做画面效果的人来说,这意味着可以像搭积木一样组织着色器代码:把通用的光照、噪声、色彩处理抽成可复用的模块,各处引用;改一处,处处生效,且立刻看到。它把"写特效"从"对着一大坨代码反复试"变成了"组合可复用的模块并实时调",是渲染表达力上的一次实打实的扩容。The engine gave shaders a "composable" capability this day: shaders can import one another, share fragments, and parameterize with macro definitions, instead of piling all code into one file. Better still, it supports cross-file hot-reload — edit a shared fragment that others reference and every shader using it refreshes instantly. For someone crafting visual effects, this means organizing shader code like building blocks: factor common lighting, noise and color processing into reusable modules referenced everywhere; change one and it takes effect everywhere, seen at once. It turns "writing effects" from "trial-and-error against one big blob" into "composing reusable modules and tuning live" — a real expansion of rendering expressiveness.

引擎统一控制台:一条执行通道,处处一致A unified engine console: one execution channel, consistent everywhere

引擎这天把"控制台"这条调试/检视通道做了统一抽象:后端收敛成单一的执行通道,命令行那侧则提供更轻量的只读检视入口。统一的好处是行为一致、心智简单——无论从哪里发起一次检视或执行,走的都是同一条规整的路径,而不是各处各写一套、行为还略有出入。这类抽象上的收敛在用户那一侧往往看不见,但它决定了系统会不会随着功能变多而越来越乱。把"控制台该怎么工作"在早期就收敛成一条权威通道,等于给后面所有要接进控制台的能力定了同一套规矩。The engine unified its "console" debug/inspect channel this day into a single abstraction: the backend converges to one execution channel, while the command-line side offers a lighter read-only inspect entry. The benefit of unifying is consistent behavior and a simpler mental model — wherever you initiate an inspect or execute, it travels the same orderly path, rather than each place having its own slightly-different version. Such convergence in abstraction is usually invisible on the user's side, but it decides whether a system grows messier as features pile up. Converging "how the console works" into one authoritative channel early sets the same rules for every capability that later plugs into the console.

新建游戏自带可运行起点 + agent 总知道你在做哪个游戏New games ship a runnable starter + the agent always knows which game

这天补上两处让"新建游戏"更顺的细节。其一:新建一个游戏时,系统会放进一个可直接运行的起点(一个转动的立方体起手式),于是你一建好就能看到画面,而不是面对空白发愣再从零写起。其二:把"当前正在做哪个游戏"这个上下文显式地喂进 agent 的系统提示里,让它清楚地知道现在该往哪个游戏里写代码。后者修的是一个很要命的隐患——多个游戏并存时,如果 agent 搞不清当前对象,很容易改错地方。把"活动游戏"做成一个明确、可靠传递的上下文,等于给 agent 装了一个不会指错的指南针。This day filled in two details that make "creating a game" smoother. One: a new game ships with a directly-runnable starter (a spinning-cube opening), so the moment you create it you see a picture, instead of staring at a blank and writing from scratch. Two: the context of "which game you're currently working on" is fed explicitly into the agent's system prompt, so it clearly knows which game to write code into. The latter fixes a dangerous pitfall — with multiple games coexisting, an agent unsure of the current target easily edits the wrong place. Making the "active game" an explicit, reliably-passed context is like giving the agent a compass that won't point wrong.

后端继续扎实:更多测试、路径脱敏、命名校验The backend keeps it solid: more tests, path redaction, name validation

后端这天延续了"用测试把行为钉死"的节奏,又补了一大批端到端探针和单元测试。重点有几处:把游戏与项目的命名规则用大量用例锁住(什么样的名字合法、什么样的该被拒,边界都有测试守着),把对外返回里的用户主目录路径继续做脱敏(不泄漏你机器上的真实路径),并把构造系统提示这类关键逻辑抽成纯函数、单独可测。这些都不是亮眼功能,而是"让一个能改你文件的系统值得信任"的日常功夫。值得一提的是,这天还顺手适配了另一种编码后端的事件格式,让接入更多模型驱动方式更顺——多一个选择,体验却保持一致。The backend kept up its rhythm of "pinning behavior down with tests," adding another large batch of end-to-end probes and unit tests. A few focuses: locking game and project naming rules with many cases (which names are valid, which should be rejected, every boundary guarded by tests), continuing to redact the user's home path in outward responses (no leaking your machine's real paths), and extracting key logic like building the system prompt into a pure, separately-testable function. None of these are flashy features; they're the daily work of "making a file-editing system worthy of trust." Notably, this day also adapted to another coding backend's event format, smoothing the integration of more model-driving options — one more choice, a consistent experience.

这一天意味着什么What this day means

把这天的几件事连起来看,主线非常清楚:让"边说边做"这件事不只是能成,而是用起来不硌手。改动即时可见(热重载)、历史完整可回(会话回放)、特效能像搭积木一样组织(可组合着色器)、agent 不会改错对象(活动游戏上下文)、后端值得托付(测试与脱敏)——每一项都在消除一个会打断心流的小摩擦。一个工具好不好用,往往不取决于它能不能做某件大事,而取决于做日常那一百件小事时顺不顺。这一天补的,正是这一百件小事里最关键的几件。Seen together, the through-line is clear: make "build while talking" not just possible but frictionless. Changes visible instantly (hot-reload), history fully recoverable (session replay), effects organized like building blocks (composable shaders), the agent never editing the wrong target (active-game context), the backend worthy of trust (tests and redaction) — each removes a small friction that would break flow. Whether a tool is pleasant to use often hinges less on whether it can do one big thing than on how smoothly it does the hundred small everyday ones. What this day filled in were several of the most crucial among those hundred.
