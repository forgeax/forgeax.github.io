每个 agent 有了会动的头像 + 工程数据有了唯一真源Animated agent avatars + one source of truth for project data

这天是个分水岭:游戏工程数据被收敛成唯一真源,整个平台读写配置都走同一个统一入口;每个 agent 在工作台里有了一张会随状态切换的动态头像;还落地了一套"宿主页面 ↔ 引擎"的对接契约和屏幕投影能力;借这次大整合,几个真实游戏暴露出来的引擎渲染 bug 也一次修干净。This day was a watershed: game-project data was converged into a single source of truth, with the whole platform reading and writing config through one unified entry; each agent gained, in the workbench, an animated avatar that shifts with its state; a "host page ↔ engine" contract and screen-projection capability landed; and through this big integration, several engine rendering bugs surfaced by real games were cleared at once.

一边收敛地基,一边增添温度Converging the foundation while adding warmth

这一天有两种气质并存。一种是冷静的"收敛":把游戏工程数据这层散落各处、各自为政的读取逻辑,统一收成唯一一个权威入口;把平台整体对齐到同一套引擎主线;把几个真实游戏暴露的引擎 bug 一次性修干净。这些都是在给地基去重、去歧义,让整个系统更可靠、更好维护。另一种是温暖的"增添":给每个 agent 配上一张会随状态变化的动态头像,让"和一群 AI 协作"这件抽象的事,第一次在画面上有了人气和临场感。一个好的平台,既要有把复杂收敛到极简的冷静,也要有让冰冷的系统透出一点人味的用心。这一天恰好把这两种气质放在了一起——既夯实了看不见的根基,也点亮了看得见的细节。Two temperaments coexisted this day. One is the cool "convergence": unifying the scattered, every-part-for-itself logic for reading game-project data into a single authoritative entry; aligning the whole platform onto one engine mainline; clearing several engine bugs surfaced by real games at once. These deduplicate and disambiguate the foundation, making the whole system more reliable and maintainable. The other is the warm "addition": giving each agent an animated avatar that changes with its state, so the abstract matter of "collaborating with a team of AIs" gains, on screen, a human presence for the first time. A good platform needs both the composure to converge complexity into simplicity and the care to let a cold system show a little humanity. This day placed both temperaments together — firming the unseen foundation and lighting up the visible details.

游戏工程数据有了唯一真源Game-project data gets a single source of truth

这天最有分量的一件事,是把每个游戏的工程配置(那份描述"这个游戏叫什么、用哪些资源、从哪个场景开始"的核心文件)收敛成了"唯一真源"。此前的痛点很典型:平台的各个部分——后端、编辑器、试玩端——各自去读这份文件、各自手写解析、各自写一段容错代码;一旦文件的格式或字段悄悄变了,谁也不能保证所有读取它的地方都同步跟上,字段对不上的隐患就此埋下。这天把它彻底统一:整个平台读写工程数据都只走同一个权威入口,这份配置的格式也用一份机器可校验的规范来自我说明——也就是说,文件长什么样、有哪些字段、各字段什么类型,都由规范本身讲清楚,不再靠散落的文档和口口相传。借这次机会还换上了更清晰的新格式:带上版本号(方便日后平滑升级)、用稳定的标识来引用资源(而不是容易变动的名字)。这件事的本质,是贯穿整个项目的一条核心信条——同一个事实只应有一个权威来源。给整个工作台的"项目文件"立一份权威说明书,换来的是更可靠、跨各处一致、出问题能在一处定位的工程数据。The weightiest thing this day was converging each game's project configuration (the core file describing "what this game is called, which resources it uses, which scene it starts from") into a "single source of truth." The prior pain was typical: each part of the platform — backend, editor, play side — read this file separately, hand-wrote its own parsing, and wrote its own error-handling; the moment the file's format or fields quietly changed, no one could guarantee every place reading it kept up, planting the hazard of mismatched fields. This day fully unified it: the whole platform reads and writes project data through one authoritative entry only, and the configuration's format describes itself with a machine-validatable spec — that is, what the file looks like, what fields it has, and each field's type are all made clear by the spec itself, no longer relying on scattered docs and word of mouth. The chance was also taken to adopt a cleaner new format: a version number (for smooth upgrades later) and stable identifiers for referencing resources (rather than easily-changing names). The essence is a core creed running through the whole project — a single fact should have only one authoritative source. Setting an authoritative manual for the workbench's "project file" buys project data that is more reliable, consistent everywhere, and diagnosable in one place.

每个 agent 有了会动的头像Each agent gets an animated avatar

这天给工作台增添了一抹很有人情味的细节:每个 agent 不再是一张静止的图片,而是一段会随状态切换的动态头像——思考时、工作时、空闲时各有不同的动画表现。这是四个部分协同完成的一件事:一批做好的角色动态头像、工作台里负责播放这些动态头像的渲染、后端一套根据 agent 当前状态来切换头像的状态机驱动,以及把这一切串起来的接口。为什么一个"会动的头像"值得专门做?因为这个平台的核心体验,是你指挥一群各有分工的 AI agent 协作干活(规划的、写设计的、写代码的……),而当它们都只是一张张静止的图标时,你很难直观感受到"现在谁在忙、忙什么"。换成会随状态变化的动态头像后,你扫一眼就能感受到"一屋子人各忙各的"那种临场感:谁在动脑、谁在跑活、谁在等。它让"和一群 AI 协作"这件原本相当抽象的事,第一次在画面上有了温度和生气——这种看似只是"好看"的细节,其实直接影响人对这套协作关系的感知和信任。This day added a humanizing detail to the workbench: each agent is no longer a static image but an animated avatar that shifts with its state — different animations for thinking, working and idle. This came together across four parts: a set of finished animated character avatars, the rendering that plays them in the workbench, a backend state machine that switches the avatar by the agent's current state, and the interface tying it all together. Why is an "animated avatar" worth building deliberately? Because the platform's core experience is directing a team of differently-tasked AI agents to collaborate (planners, designers, coders...), and when they're all just static icons, it's hard to intuit "who's busy now, with what." With avatars that change by state, a glance conveys the "a room full of people each at their own work" presence: who's deliberating, who's running a job, who's waiting. It gives the once-abstract matter of "collaborating with a team of AIs" warmth and life on screen for the first time — a seemingly "just pretty" detail that actually directly shapes how people perceive and trust this collaborative relationship.

宿主页面 ↔ 引擎对接契约 + 屏幕投影A host-page ↔ engine contract + screen projection

引擎这天还立了一份"宿主页面 ↔ 引擎"的对接契约,并补上了一项很实用的能力:把三维世界里的一个点投影到屏幕上的二维坐标。先说契约:游戏跑在引擎里,而它外面包着一层网页界面(宿主),两者之间需要清楚约定"谁能向谁要什么、传什么"——把这份约定明确写下来,跨这层边界的协作就不再靠默契和猜测。再说屏幕投影:它解决的是一个非常常见的需求——怎么把一块界面元素"钉"在一个三维物体上方?比如让血条飘在敌人头顶、让名字标签跟着角色移动、让一个交互提示出现在某个物品旁边。要做到这些,就得能把那个三维物体在世界里的位置,实时换算成它当前在屏幕上的二维落点。这天把这套世界坐标到屏幕坐标的换算做成了引擎的标准能力,还配了相机自动适配画面比例、以及一个视频过场演示。这些能力合起来,让"在三维画面之上叠加二维信息层"这件几乎每个游戏都要做的事,有了可靠的底层支持。The engine also established a "host-page ↔ engine" contract this day and added a very practical capability: projecting a point in the 3D world to its 2D coordinate on screen. The contract first: a game runs in the engine, wrapped by a web interface (the host) outside it, and the two need a clear agreement on "who can ask whom for what, passing what" — writing this agreement down explicitly means collaboration across that boundary no longer relies on tacit understanding and guessing. Screen projection next: it solves a very common need — how to "pin" a UI element above a 3D object? Such as a health bar floating over an enemy's head, a name tag following a character, an interaction prompt appearing beside an item. Achieving these requires converting that 3D object's world position, in real time, into its current 2D landing point on screen. This day made this world-to-screen conversion a standard engine capability, with camera auto-fit to the picture's aspect ratio and a video-cutscene demo alongside. Together these give reliable underpinning to "overlaying a 2D information layer atop a 3D picture" — something nearly every game must do.

真实游戏照出的引擎 bug,一次修干净Engine bugs surfaced by real games, fixed at once

随着工程数据的统一,整个平台这天也彻底对齐到了同一套引擎主线上。这次大整合带来一个意外但宝贵的收获:几个之前在做真实游戏时暴露出来的引擎问题,被一次性确认修复——包括大场景的阴影、某一类数据的写入、资源标识相互撞车、以及纯色环境光等四个具体问题。这件事印证了一条健康的协作闭环:用真实的游戏去"压测"底层引擎,往往能照出抽象测试照不出的真实问题;把这些问题如实记录、推动修复、再确认落地,引擎就在一轮轮真实使用中变得越来越扎实。这天编辑器和全部六个样例游戏也一并迁到了引擎新的接口上。统一带来的好处是显而易见的:各处行为一致、问题更好追溯、以后做新特性也能"一次实现、处处生效",不必在多个分叉的版本之间来回兼容。把分散的收敛成统一的,看似只是整理,实则是为后面所有的快速迭代扫清了障碍。As project data unified, the whole platform also fully aligned onto one engine mainline this day. This big integration brought an unexpected but valuable gain: several engine issues previously surfaced while building real games were confirmed fixed at once — including large-scene shadows, a class of data writes, resource-identifier collisions, and solid-color ambient light, four concrete problems. This confirms a healthy collaborative loop: stress-testing the underlying engine with real games often surfaces real problems that abstract tests can't; recording them faithfully, driving the fixes, and confirming they land makes the engine ever more solid through rounds of real use. This day the editor and all six sample games were migrated to the engine's new interface too. The benefit of unification is obvious: behavior is consistent everywhere, problems are easier to trace, and new features can be "built once and take effect everywhere," with no juggling compatibility across forked versions. Converging the scattered into the unified looks like mere tidying but actually clears the obstacles for all the fast iteration that follows.

A truly good tool must both set order seamlessly underneath and make people comfortable, even happy, to use on top. This day attended to both.
