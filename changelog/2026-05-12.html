一昼夜四条线:这一天的全景Four tracks in a day: the day's panorama

这是迄今最密集的一天,从午夜一直推到次日清晨,四条线同时在跑:引擎在一套严格的七步闭环流程下连推多个特性与修复、聊天面板进入"永不收工"的稳态打磨、后端把安全与接口契约用测试一条条钉死、再加上收官时一场把界面热更新独立出来的大重构。把这么多动作压在一天里而不乱,靠的是两件事:一是每条线都有清晰的边界和验收标准,二是越靠近地基的改动越要可验证。下面按主题拆开讲,但要记住它们是同一天里咬合着往前滚的。This was the densest day so far, pushing from midnight into the next morning with four tracks running at once: the engine landing feature after feature and fix under a strict seven-step closed loop, the chat panel entering "never finished" steady-state polish, the backend nailing safety and interface contracts down with tests one by one, plus a closing refactor that pulled the interface's hot-reload out on its own. Packing so much into one day without chaos came down to two things: each track had clear boundaries and acceptance criteria, and the closer a change was to the foundation, the more it had to be verifiable. Below it's split by theme, but remember they rolled forward meshed together in a single day.

引擎资产系统 v1:用句柄引用游戏内容Engine asset system v1: referencing game content by handle

这天引擎最重要的交付,是第一版资产系统。在此之前,模型、纹理、场景这些"游戏内容"还没有一套统一的管理方式;资产系统给了它们一个正式的身份:每一份资产都是一个结构化的对象,通过一个轻量的"句柄"来引用,而不是到处传递庞大的原始数据。句柄就像图书馆的索书号——你拿着它就能取到那本书,却不必把整本书抱在手里到处走。配套还做了一个示例房间场景来验证整条链路。这套机制的意义在于:从此游戏内容可以被结构化地引用、共享和复用,加载模型、贴图、场景都有了统一的入口。它是后面所有"导入一个模型、把素材摆进场景"功能的真正起点。The engine's most important delivery this day was the first version of an asset system. Before it, "game content" like models, textures and scenes had no unified way to be managed; the asset system gave them a formal identity: every asset is a structured object referenced through a lightweight "handle" rather than passing huge raw data around. A handle is like a library call number — hold it and you can fetch the book, without carrying the whole book around. A sample room scene was built to validate the chain. The significance: game content can now be referenced, shared and reused in a structured way, with one entry point for loading models, textures and scenes. It's the true starting point for every later "import a model, place assets in a scene" feature.

逐像素对齐基准:渲染质量不许偷偷退化A pixel-parity benchmark: render quality can't quietly regress

自研渲染最怕的不是某次画错,而是"悄悄变差却没人发现"——改了一处,某些画面比对照差了几个像素,肉眼一时看不出,日积月累就跑偏了。这天立了一把"逐像素对齐"的尺:用一个参照来逐像素比对引擎渲染出的画面,只要差异超出阈值,持续集成就直接亮红、当场拦下,不让有问题的改动合进主干。它把"渲染对不对"从一件靠人盯、靠感觉的事,变成了一道自动、客观、每次提交都跑的关卡。对一个要长期演进画质的引擎来说,这道守门是质量能稳住的前提——有了它,大胆改渲染才不至于提心吊胆。What an in-house renderer fears most isn't a single wrong frame but "quietly getting worse with no one noticing" — change one thing and some frames differ from the reference by a few pixels, invisible to the eye yet drifting off over time. This day raised a "pixel-parity" yardstick: compare the engine's rendered frames against a reference pixel by pixel, and the moment the difference exceeds a threshold, continuous integration goes red and blocks the change from merging into the trunk. It turns "is the rendering correct" from something watched by hand and by feel into an automatic, objective gate that runs on every commit. For an engine evolving its image quality long-term, this gate is the precondition for quality holding steady — with it, you can change rendering boldly without dread.

沙盒视觉验证:让 agent 自己"看"画面对不对Sandbox visual verification: let the agent "see" whether the picture is right

让 AI 自动改游戏,有个绕不开的难题:它改完之后,怎么知道画面真的对了?如果只看代码有没有报错,很容易"代码没崩、但画面是黑的"还自以为成功。这天在沙盒里搭起一套视觉验证机制,并刻意把"生产画面"和"检查画面"两个角色分开:一边负责把游戏跑起来、截出画面,另一边负责对截出的画面做判断。角色分离的好处是验证更可信——不会出现"自己改、自己拍、自己说没问题"的自证陷阱。这一步是让 agent 从"会写代码"走向"会对自己的产出负责"的关键:它不再只是把代码丢出去,而是能闭着环看一眼"我做出来的东西到底长什么样"。Having an AI edit games automatically runs into an unavoidable problem: after it changes things, how does it know the picture is actually right? Checking only whether the code errored easily leads to "the code didn't crash but the screen is black" while believing it succeeded. This day built a visual verification mechanism in the sandbox, deliberately separating two roles — "producing the picture" and "checking the picture": one side runs the game and captures frames, the other judges the captured frames. Separating the roles makes verification more trustworthy — no "I edit, I screenshot, I declare it fine" self-certification trap. This step is key to the agent moving from "can write code" to "is accountable for its output": it no longer just throws code over the wall but can close the loop and look at "what does the thing I made actually look like."

实例化渲染 + 多物体:一个方块小游戏当试金石Instanced rendering + many objects: a block game as the touchstone

这天还用一个"方块下落消除"的小游戏 demo 来锤打引擎的多物体能力。这类游戏的特点是同屏会出现大量长得一样的方块,如果每一个都单独发一条绘制指令,开销会很快堆起来。引擎为此加上了"实例化绘制":一次提交就能画出大批同种物体,把重复开销摊薄。配套还梳理了多物体的渲染路径,让"很多个实体一起出现"这件事走得又快又稳。用一个真正能玩的小游戏来验证,而不是抽象的测试,这本身也是一种纪律——能让一个真实游戏跑顺,远比跑通一段孤立的示例代码更有说服力。This day also hammered the engine's many-object capability with a "falling-block clear" mini-game demo. Such games feature lots of identical blocks on screen at once, and issuing a separate draw command for each piles up cost fast. For this the engine added "instanced drawing": a single submission draws a large batch of the same object, amortizing the repeated cost. The many-object rendering path was tidied alongside, so "many entities appearing together" runs fast and stable. Validating with a genuinely playable mini-game rather than an abstract test is itself a discipline — making a real game run smoothly is far more convincing than passing an isolated snippet.

聊天面板上百拍稳态打磨:成本、时长、多供应商~100 chat-polish passes: cost, duration, multiple providers

聊天面板这天进入"永不收工"的稳态打磨,上百次极小迭代集中在几件实用的事上。其一是把每一轮对话的真实成本和耗时显示出来,还做了自适应的金额格式——几分钱、几毛、几块各用合适的精度,让花了多少一目了然。其二是给"用哪个编码后端"做了一个可切换的选择器:可以为某次对话指定走哪一家,选择会被记住、能跨标签页同步、支持键盘上下选,还会在你选的那家不可用时给出提示。其三是把"模型在长时间静默思考"这种容易让人焦虑的状态做了体贴处理——显示已等待秒数、超过一定时间建议切换、对"跑完却没有可见输出"的情况给出占位说明。每一拍只动一处、改完自测、再记一笔。这条线之所以值得花上百拍,是因为它是用户每天盯得最久的界面:能力再强,读起来费劲、用起来心里没底,就谈不上信任。The chat panel entered "never finished" steady-state polish this day, a hundred-plus tiny iterations focused on a few practical things. One: surface each turn's real cost and duration, with an adaptive amount format — cents, dimes, dollars each at the right precision — so you see at a glance what it cost. Two: a switchable selector for "which coding backend to use": you can pin a conversation to one, the choice is remembered, syncs across tabs, supports up/down keyboard selection, and warns when the one you picked is unavailable. Three: thoughtful handling of the anxiety-inducing "the model is thinking silently for a long time" state — showing seconds elapsed, suggesting a switch past a threshold, and a placeholder note for "finished but no visible output." Each pass touched one thing, self-tested, and logged a note. This track earns a hundred passes because it's the surface the user stares at longest each day: however strong the capability, if it reads laboriously and feels uncertain, there's no trust.

后端的安全与契约加固:白名单、防穿越、大量测试Backend safety and contract hardening: whitelists, traversal defense, many tests

既然 agent 会真的读写你机器上的文件,后端这层就必须把"它只能碰该碰的东西"这件事做死。这天围绕文件与路径安全扎了一大批防线和测试:用白名单约束允许访问的路径、加上对"目录穿越"这类越权访问的防御、让写文件时拒绝覆盖一个已存在的目录、把对外返回里的用户主目录路径做脱敏(避免泄漏你机器上的真实路径)。与此同时,后端的各种接口契约也被一条条用测试钉住——什么样的输入该返回什么、边界情况怎么处理,都有测试守着,当天单元测试数量跨过了一个里程碑。这些工作没有一个是"看得见的新功能",但它们决定了你敢不敢把一个能动手改文件的 AI 放进自己的项目里:边界清楚、行为可预期、回归有测试兜着,才谈得上放心。Since the agent really reads and writes files on your machine, the backend must make "it can only touch what it should" airtight. This day laid a large batch of defenses and tests around file and path safety: constraining accessible paths with a whitelist, adding defense against "directory traversal" over-reach, refusing to overwrite an existing directory when writing a file, and redacting the user's home path in outward responses (so your machine's real paths don't leak). Meanwhile the backend's interface contracts were pinned down test by test — what input should return what, how edge cases are handled, all guarded by tests, and the unit-test count crossed a milestone that day. None of this is a "visible new feature," but it decides whether you dare let a file-editing AI into your own project: only with clear boundaries, predictable behavior and regressions caught by tests is there real peace of mind.

收官重构:界面热更新独立化A closing refactor: making the interface's hot-reload independent

跨到次日凌晨,这天用一场结构上的大重构收了官:把界面的热更新机制独立出来,并顺势把各部分各归其位——用户的游戏数据迁到实例自己的目录、引擎源码抽到统一的构建位置、环境配置上移到主仓根部、并理顺了嵌套目录里容易踩坑的布局。这类重构在用户那一侧几乎看不见任何变化,但它把"改一处代码、界面立刻热更"这条开发体验做得更干净、更不容易互相牵连。地基越清楚,后面盖得越快——把这件事放在一天的最后做,正是因为前面那么多新东西落下来之后,需要一次收拢让整棵树重新对齐。Crossing into the early hours, the day closed with a structural refactor: making the interface's hot-reload mechanism independent, and putting each part in its place along the way — the user's game data moved to the instance's own directory, the engine source extracted to a unified build location, environment config lifted to the repo root, and the pitfall-prone nested-directory layout straightened out. Such a refactor shows almost no change on the user's side, but it makes the "edit code, the interface hot-reloads instantly" experience cleaner and less prone to cross-interference. The clearer the foundation, the faster you build later — doing this at the day's end is precisely because, after so many new things landed, the whole tree needed one consolidation to realign.

这一天意味着什么What this day means

如果说前几天证明了"对话能做出能跑的东西",这一天是在为"能不能长期、可靠地做下去"打地基。资产系统让内容可被结构化管理,逐像素基准与沙盒视觉验证让"做出来的画面对不对"有了客观裁判,后端的安全与测试让"放手让 AI 动手"变得可信,聊天打磨让人愿意每天用,收官重构让这一切在工程上保持整洁。它们合起来透露出一种取向:既要往前冲得快,也要在每一步都留下能验证、能回归、能复盘的扎实痕迹。这正是这份日志想给未来开发留下的范本——速度与严谨不是二选一,而是同一天里可以兼得的两件事。If the previous days proved "conversation can build something runnable," this day laid the foundation for "can it be done reliably, long-term." The asset system lets content be managed structurally; the pixel-parity benchmark and sandbox visual verification give an objective judge of "is the picture right"; the backend's safety and tests make "letting the AI act" trustworthy; the chat polish makes people want to use it daily; and the closing refactor keeps it all clean in engineering terms. Together they reveal a stance: charge forward fast, yet leave at every step a solid trail that can be verified, regressed and retrospected. That's exactly the model this log wants to leave for future development — speed and rigor aren't an either/or, but two things attainable in the same day.
