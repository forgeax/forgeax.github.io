这天做了两件让"发版"变得真正自动化的事:一是接上了企业微信群机器人,可以从群里一键触发构建、也能在发版后自动推送通知;二是把夜间发布的 CI 流水线从头到尾调通——修掉了 Git 认证冲突、残留分支处理、以及把定时频率回归到合理的工作日计划。另外,bun fx update 命令加上了彩色结构化的更新报告,每次拉代码后一目了然。This day did two things to make "releasing" truly automatic: first, a WeChat Work (WeCom) group robot was connected, able to trigger builds from the chat group and push notifications after a release; second, the nightly release CI pipeline was debugged end to end — fixing git auth conflicts, stale branch handling, and returning the schedule to a sensible weekday cadence. On top of that, bun fx update gained a colorful, structured update report, making every code pull crystal clear at a glance.

企业微信群机器人:从聊天群触发构建WeCom group robot: trigger builds from the chat

做游戏的团队通常都在企业微信群里沟通。之前要触发一次构建,得登 GitHub 手动点 workflow,或者等定时任务自己跑——这对非技术成员来说门槛太高。这天把企业微信群机器人接了进来:在群里发一条指令,就能通过 GitHub 的 repository_dispatch API 触发一次完整的构建和发布流程;发版完成后,机器人会自动把版本号、更新内容、下载链接推回群里。这意味着"要发版"这件事,从此不需要开发者去碰 GitHub——产品经理在群里说一句"发一版",机器人就能替他跑完全部流程。这是让自动化真正服务团队的一步。Game teams usually communicate in WeChat Work groups. Before, triggering a build meant logging into GitHub and manually clicking a workflow, or waiting for the scheduled task — too high a bar for non-technical members. This day connected a WeCom group robot: send a command in the group and it triggers a full build-and-release via GitHub's repository_dispatch API; when the release is done, the robot automatically pushes the version number, changelog and download link back to the group. This means "let's release" no longer requires a developer to touch GitHub — a product manager can say "ship a build" in the group and the robot runs the entire pipeline. It's a step toward automation truly serving the team.

发布流水线:从"经常坏"到"全链路通"The release pipeline: from "often broken" to "end-to-end green"

夜间自动发布流水线昨天刚建好,今天就进入了"把每个环节调通"的阶段。先是发现 Git 推送时会出现"Duplicate header: Authorization"错误——原因是 GitHub Actions 的 checkout 动作和 workflow 里自己设的 token 冲突,两个认证头打架。修法是改用 token-in-URL 的方式（把 PAT 嵌在 remote URL 里），绕过 header 冲突。接着发现多次失败留下的残留 release 分支会阻塞新一轮发布——于是加了自动清理逻辑:每次发布前先检查有没有同名的旧分支和旧 PR,有就关掉、删掉,再重新来。最后把频率从"每 10 分钟跑一次"（之前为了调试临时设的）改回"工作日早上 10 点"。三个修复叠在一起,流水线从"有时能跑有时报错"变成了"每个工作日准时、稳定地产出一个新版本"。The nightly auto-release pipeline was just built yesterday and immediately entered the "debug every link in the chain" phase today. First came a "Duplicate header: Authorization" error on git push — caused by a conflict between the checkout action's auth header and the workflow's own token, two authorization headers fighting. The fix was to switch to token-in-URL auth (embedding the PAT in the remote URL), sidestepping the header collision. Next, leftover release branches from previous failed runs blocked new releases — so auto-cleanup logic was added: before each release, check for any same-named old branches and PRs, close and delete them, then start fresh. Finally the schedule was changed from "every 10 minutes" (temporarily set for debugging) back to "weekdays at 10 AM." The three fixes together took the pipeline from "sometimes runs, sometimes errors" to "reliably producing a new version on time every workday."

bun fx update:拉完代码一目了然bun fx update: pull code and see everything at a glance

开发者每天早上做的第一件事通常是拉最新代码。之前 bun fx update 就是安静地跑一遍 git pull + 子模块同步,成功了就什么也不说,失败了就丢一段难懂的报错。这天给它加上了结构化的更新报告:用彩色的表格显示每个子模块的拉取结果（成功 / 跳过 / 冲突）、当前分支、最新 commit 摘要。如果某个子模块有本地修改需要 stash,也会明确告诉你。一次 update 结束后,你对"整个项目现在什么状态"心里有数——不用再挨个子模块去 git status。小改动,但每天用、每个人用,积少成多就是体验的提升。The first thing a developer does each morning is usually pull the latest code. Before, bun fx update would silently run git pull + submodule sync — say nothing on success, and dump an opaque error on failure. This day added a structured update report: a color-coded table showing each submodule's pull result (success / skipped / conflict), its current branch, and the latest commit summary. If a submodule has local changes that needed stashing, it tells you explicitly. After one update you know "what state the entire project is in" — no more running git status in each submodule one by one. A small change, but used daily by everyone, and small improvements compound into real experience gains.

镜像安全:堵住 token 泄漏 + PR 阶段 dry-runMirror security: plugging a token leak + PR-stage dry-run

还修掉了一个安全问题:之前的镜像同步脚本在日志中不小心打印了 MIRROR_TOKEN 的值,虽然日志只有仓库管理员能看到,但 token 出现在任何日志里都是不可接受的。这天把它修掉了,同时加了一个 PR 阶段的镜像 dry-run 检查——每次提 PR 时,自动跑一遍镜像同步的"干跑"(不真正推送),提前发现配置问题,而不是等合并后真正同步时才暴出来。安全这件事,修一个漏洞不难,难的是建立习惯:每个碰 token 的地方都加 mask,每个流程都加预检。这天补了两层。A security issue was also fixed: the mirror sync script was accidentally printing the MIRROR_TOKEN value in logs — and while only repo admins can see the logs, a token appearing in any log at all is unacceptable. This day fixed it and also added a PR-stage mirror dry-run check — every time a PR is opened, the mirror sync runs in "dry mode" (no actual push) to catch configuration issues early, instead of only discovering them after merge when the real sync runs. Security isn't hard when it's about patching one leak; what's hard is building the habit: mask every token, add a pre-check to every flow. This day added two layers of that.

这一天的主题是"闭环"。昨天建的流水线今天调通了,昨天接的镜像今天加固了,企微机器人把"触发 → 构建 → 通知"串成了一条线。每一环单独看都不复杂,但真正的价值在于它们连成了环:群里说一句话 → GitHub 跑流水线 → 代码测试构建打包 → 通知推回群里。当这条环跑通,团队就从"手动发版"进化到了"对话发版"——自动化不再只是开发者的工具,而是整个团队的基础设施。The theme of this day is "closing the loop." Yesterday's pipeline was debugged today, yesterday's mirror was hardened today, and the WeCom robot strung "trigger → build → notify" into one line. Each link is simple on its own, but the real value is in them forming a loop: say something in the group → GitHub runs the pipeline → code tests, builds, packages → notification pushed back to the group. When this loop runs, the team evolves from "releasing by hand" to "releasing by conversation" — automation is no longer just a developer tool, but infrastructure for the whole team.
